## 二、发现的漏洞 (Bugs)

### 2.1 [MEDIUM] pool_scanner.py: `best_buy_days` 首次引用时未定义

**文件**: pool_scanner.py:128
**代码**:
```python
if score > best_score or (score == best_score and days_ago < (best_buy_days if best_buy else 999)):
```

`best_buy_days` 只在 131 行赋值（`best_buy_days = days_ago`），之前不存在。

**实际影响**: 第一次迭代时 `best_score=0`，`score > 0` 为 True，短路求值不会触发右侧，所以低概率触发。但不符合编码规范，IDE 会报黄线。

### 2.2 [MEDIUM] pool_scanner.py L128: `best_buy_days` 未声明

同 2.1，合并处理。

### 2.3 [MEDIUM] pool_screener.py `run_phase1()`: 全局污染

**文件**: pool_screener.py:57-60
**代码**:
```python
pool_scanner.load_a500_pool = lambda: original_pool()[:test_n]
pool_scanner.SCORE_THRESHOLD = 0
```

修改了 `pool_scanner` 模块的全局变量。如果测试后直接跑 `--from-cache`，`SCORE_THRESHOLD` 仍为 0，会加载 `all_valid` 中的 score=0 的垃圾股进入 Phase 2。

**修复**: 在 `run_phase1()` 退出前恢复原值。

### 2.4 [MEDIUM] pool_screener.py L276: `tech_result` 可能为 None 导致 AttributeError

**代码**:
```python
tech_result = compute_technical_score(analyzer, None, recent_buy)
tech_score = tech_result.get('tech_score', ...)
```

外层 try/except 捕获了，但异常信息被吞掉（`except Exception as te: tech_score = c['score'] * 20`），`te` 变量未使用。

### 2.5 [LOW] pool_screener.py L216: `macd_status` 在非 None 路径可能未赋值

当 `best_buy is not None` 时走 else 分支直接读 `analyzer.macd_data[-1]`，如果 macd_data 为空会 IndexError。概率极低（ChunLun 分析总是带 MACD）。

## 三、逻辑缺陷

### 3.1 [HIGH] `scan_news()` 消息面评分逻辑偏向利空

**文件**: pool_screener.py:164-176
**问题**: 评分先判断负面向，再判断正面向。如果同时有 2 个负面词和 3 个正面词，会走到 `neg_count >= 1` → `max(35, 50 - 2*4) = 42`（利空），而不是 `pos_count >= 3` → `min(75, 50 + 3*6) = 68`（利好）。

**影响**: 对多空交织的新闻（最常见情况），系统偏向利空解读。

### 3.2 [MEDIUM] `full_rescore.py` vs `pool_screener.py` 的 COMPOSITE_THRESHOLD 不一致

- `pool_screener.py` Phase 3: 只给综合分 ≥ 40 的股票生成报告
- `full_rescore.py`: 不论综合分多少，全量 Top 10 都生成报告

如果 Top 10 中有综合分 < 40 的股票（如 C 级），仍然会生成"推荐"报告，与三维系统的"< 40 不推荐"原则矛盾。

### 3.3 [MEDIUM] Phase 1 评分 2 分股票（60-250天买点）完全丢失信息

Phase 1 给了 score=2 的股票（60天以上买点）有 pattern 信息（如"中枢上沿附近"），但被 `SCORE_THRESHOLD = 3` 筛掉后，这些股票的缠论分析结果也丢弃了。如果后续想调整阈值（比如放宽到 score≥2 看看），需要重跑 Phase 1。

### 3.4 [LOW] 估分表与真实分差距太大

| scan score | 估分 tech | 实际案例 tech |
|:----------:|:---------:|:------------:|
| 5 | 86 | 哈投股份=70，中国天楹=68 |
| 4 | 75 | 中信证券=86，海康威视=84 |

score=5 的股票被高估 16+ 分，score=4 的被低估 9+ 分。这说明 scan score（时间维度）和真实技术分（空间维度）并不线性相关。

## 五、性能 / 运维问题

### 5.1 [MEDIUM] Baostock 强制重连增加 30% 耗时
`get_fundamentals()` 每次先 logout 再 login 保证 session 新鲜，但每次重连耗时 2-3 秒。120 只 × 3s = 360s 纯浪费。

**建议**: 改为只在 Phase 2 入口 login 一次，每批内部复用 session。

### 5.2 [MEDIUM] Phase 2 失败无断点续传
如果 Phase 2 在第 100 只股票崩溃，前面 99 只的结果全丢。`_save_phase2_results` 只在全部完成后调用。

**建议**: 每批完成后增量追加保存。

### 5.3 [LOW] 报告文件覆盖无警告
`pool_screener.py` 和 `full_rescore.py` 生成同名文件（`扫描汇总_{date}.md`），后者静默覆盖前者。用户可能困惑为什么"推荐列表变了"。

### 5.4 [LOW] HTML 生成使用 RecursiveTimingSystem 而非 ChanLunAnalyzer
`full_rescore.py` L342-346 调用 `RecursiveTimingSystem.run_full_analysis()` 会额外加载 30 分钟 K 线（Baostock 单次 2-3 秒），10 只浪费 20-30 秒。

**建议**: 改为直接使用 `ChanLunAnalyzer`（仅日线），与 pool_scanner 一致。
