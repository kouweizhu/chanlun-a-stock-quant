## 🔴 严重Bug（5个）

### Bug 1: 最终平仓未扣手续费
- **位置**: `backtest_engine.py` 最终平仓处
- **现象**: 回测结束时强制平仓，只加了市值，没有扣除卖出佣金。其他4个卖出点（信号卖出/止损/止盈）都正确扣除了手续费，唯独最终平仓遗漏。
- **影响**: 每笔最终平仓虚增约0.03%收益，累积偏差显著
- **修复**: `cash += (shares * last_price) * (1 - BACKTEST_COMMISSION)`

### Bug 2: TradeRecord.position_pct 始终为 0
- **位置**: `backtest_engine.py` 所有4处TradeRecord创建点
- **现象**: dataclass定义了 `position_pct: float` 字段，但在所有创建点都硬编码为0，从未填充实际仓位比例。统计输出时该字段也被跳过。
- **影响**: 数据结构不完整，下游消费者无法获取每笔交易的实际仓位占比
- **修复**: 计算 `lot['shares'] * lot['price'] / self.initial_capital` 填入

### Bug 3: SlippageModel.estimate_avg_daily_volume 计算错误
- **位置**: `slippage_model.py` estimate_avg_daily_volume()
- **现象**: 使用 `mean(volume) * mean(close)` 来估算日均成交额，正确公式应该是 `mean(volume * close)`。两者不等价，因为成交量和收盘价存在协方差。
- **影响**: 系统性低估高波动股票的日均成交额，导致滑点估算偏高约5-30%
- **修复**: `return float((df['volume'] * df['close']).mean())`

### Bug 4: rescore_news.py 硬编码权重和阈值
- **位置**: `rescore_news.py` 第54行/67-78行
- **现象**: 硬编码 `w_tech=0.4, w_fund=0.3, w_news=0.3`，不从 config_loader 导入。等级阈值被抬高：config.yaml A≥70/B≥60/C≥50，但 rescore_news.py 是 A≥70/B≥65/C≥55。
- **影响**: 综合分60-64的股票在主系统得B级，在 rescore_news.py 补扫后得C级
- **修复**: 统一从 config_loader 读取权重和阈值

### Bug 5: full_rescore.py MD报告等级阈值标注错误
- **位置**: `full_rescore.py` 第307行
- **现象**: 报告标注 `A≥80 B≥65 C≥50`，实际 config.yaml 是 `A≥70 B≥60 C≥50`
- **影响**: 用户误以为需要80分才A级，低估系统评分能力
- **修复**: 从 config_loader 动态读取等级阈值

## 🟡 逻辑偏差（7个）

### 偏差1: 30分钟下跌笔过滤过于严苛
- **位置**: `backtest_engine.py` `_check_m30_downtrend()` + `generate_analysis.py` `_check_m30_downtrend()`
- **现象**: 连续≥2支下跌笔就拦截三类买点。但三类买点的定义本身就是"回调不破中枢上沿后的回升"，回调在30分钟图上天然表现为1-2支下跌笔。标准三买形态被误杀。
- **建议**: 改为≥3支连续下跌笔，或增加条件：下跌笔的低点必须高于日线中枢ZG

### 偏差2: 止损三层检查顺序不当
- **位置**: `backtest_engine.py` `_check_stop_loss()`
- **现象**: 当前顺序：硬止损(-8%) → 结构止损 → 次级别卖点。硬止损最宽松，结构止损通常更紧（中枢ZG一般在入场价下方3-6%）。止损原因记录错误。
- **建议**: 调整为：结构止损（最紧）→ 次级别卖点 → 硬止损（最后防线）

### 偏差3: score_backtest.py 两套评分逻辑并存
- **位置**: `score_backtest.py` `calc_tech_score()` 路径A vs 路径B
- **现象**: 有近期买点时调用 `compute_technical_score()`（4维度叠加），无近期买点时用自己一套加减分逻辑（笔方向+/−、中枢位置+/−）。两套逻辑结构完全不同。
- **建议**: 统一为单一评分函数

### 偏差4: scan_news() 搜索查询只搜负面
- **位置**: `pool_screener.py` 第160行
- **现象**: `query = f"{name} {code} 利空 公告 风险"` 只搜利空/公告/风险。虽然后续关键词匹配同时统计正负面，但返回的文章本身就是按"利空"检索的——利好新闻可能根本没被搜到。
- **建议**: 同时发起正面和负面两次搜索，或合并为 `利好 OR 利空`

### 偏差5: full_rescore.py 技术分回退估分用魔法数字
- **位置**: `full_rescore.py` 第58-60行
- **现象**: `tech_score = {5: 86, 3: 65}.get(int(c['score']), 50)` — Phase1的score(1-5)与真实技术评分(0-100)的映射是拍脑袋的。默认fund_score=70也无依据。
- **建议**: 当 .phase2_results.json 缺失时打印大号警告，或拒绝运行

### 偏差6: 滑点公式与文档分层表严重不一致
- **位置**: `slippage_model.py`
- **现象**: 公式产出 100亿→0.1%，但文档标注 0.01%——差了10倍。文档严重误导。
- **建议**: 确认哪个是作者本意，统一修正

### 偏差7: score_backtest.py 仓位逻辑与主系统脱节
- **位置**: `score_backtest.py` `classify_position()`
- **现象**: 仅根据 tech_score 决定仓位（≥80→30-50%），完全忽略基本面约束。主系统的仓位逻辑是 tech_score 决定能否买，fund_score 决定能买多少。
- **建议**: 使用 `compute_3d_score()` 返回的 position 值
