# 技术评分回测验证方法论

## 适用场景

当以下条件同时满足时使用：

1. 你有一套**分析引擎**（如缠论分析器或基本面评分模型）能在历史数据上产生评分
2. 你有一个**评分模型**（如 [-30,100] 技术评分，或 [0,100] 基本面四维评分）
3. 需要验证这个评分是否真的能预测后续价格走势

**两个子类：**

| 回测类型 | 数据频率 | 评分引擎 | 脚本 |
|:--------|:--------|:---------|:----:|
| **技术面** | 每周一采样 | ChanLunAnalyzer + v3.0评分规则 [-30,100] | `score_backtest.py` |
| **基本面** | 每财报季一次（年报/半年报/季报披露截止日） | quick_fundamental.calculate_fundamental_score [0,100] | `fund_backtest.py` |

**典型触发词：**
- "验证一下这个评分系统有没有用"
- "这个评分和实际走势的相关性怎么样"
- "做个回测验证评分是否有效"
- "技术面和基本面都回测一下"

**不适用场景：**
- 纯回测（只问收益不问评分预测力）→ 用已有回测引擎
- 缠论理论审计 → 用 `chanlun-code-audit`
- 构建评分模型本身 → 用 `daily-chanlun-timing-system`

## 核心方法论

### 验证假设

**单方向假设**：评分高的信号，买入后 N 日收益率显著高于评分低的信号。

**双方向验证**：
1. **分组对比**：A/B/C 不同评分等级，后续收益是否单调递减？
2. **相关性检验**：评分与收益率的相关系数 r 是否显著大于 0？

### 评分推导方法论

评分不应凭空产生，应从分析状态中客观推导：

| 评分维度 | 数据来源 | 评分逻辑 |
|---------|---------|---------|
| 趋势结构 | 中枢位置 (ZG/ZD) | 在中枢底附近买=高分，追高买=低分 |
| 信号质量 | 买卖点级别 (level=1/2/3) | 一买>二买>三买，按中枢位置细分为9档 |
| 多级别共振 | 次级别确认状态 + MACD柱收缩 | 次级别出买点=高分，MACD柱收缩=加分 |
| 量价辅助 | 成交量相对均值 | 缩量止跌=高分，放量下跌=低分 |
| 波动率 (v1.1) | 近60日收盘价波动率 | 高波动成长股+量价辅助，低波动蓝筹+结构分数 |

**买点类型识别**（v1.1 修复）：使用 `point.level` 而非 `point.type`。
- `point.type` → 只返回 'buy'/'sell'（无细分）
- `point.level` → 1=一买, 2=二买, 3=三买（提供信号分级）

**信号质量 9 档细分**（v1.1 新增）：
| 类型 | 中枢底部 | 中枢中轴下 | 中枢上 |
|:----:|:--------:|:----------:|:------:|
| 一买 | 30分 | 28分 | 25分 |
| 二买 | 25分 | 22分 | 20分 |
| 三买 | 22分 | 18分 | 14分 |

**波动率因子**（v1.1 新增）：
- 计算 recent 60日收盘价 std/mean
- 波动率 > 0.3（成长股）→ 量价配合好时 +0~3分
- 波动率 < 0.15（蓝筹股）→ 结构可靠时 +0~2分
- 上限 5 分

**关键原则**：评分必须在买入信号发生时点可计算，不能使用未来数据。

### 输出分析报告

#### 1. 按评分等级分组

```
A+ (均分86, 14次): 5日=+6.28%, 10日=+5.80%, 20日=+6.89%, 60日=+3.64%
A  (均分84, 27次): 5日=+5.11%, 10日=+4.47%, 20日=+4.63%, 60日=+10.56%
B  (均分59, 11次): 5日=+4.56%, 10日=+4.63%, 20日=+1.82%, 60日=-3.83%
```

**观察要点**：
- A 级 > B 级？→ 区分度有效
- 中长期（20日/60日）差异是否大于短期？→ 评分更适用于长周期决策
- 如果差异不明显 → 评分因子权重需要调整
- **v1.1 经验**：A+（短期爆发强）vs A（中长期稳健），两者特征不同，可分别用于短线和中线策略

#### 2. 相关系数

```
技术评分 vs 5日后收益率: r = 0.193
技术评分 vs 20日后收益率: r = 0.265
技术评分 vs 60日后收益率: r = 0.293
```

**解读**：
- r < 0.1: 基本无关，评分模型无效
- r 0.1-0.3: 弱到中等正相关，有一定预测力
- r > 0.3: 显著正相关，评分可以纳入决策
- r > 0.5: 强相关，评分可作为主要决策依据

#### 3. 按股票类型分组

| 类型 | 5日 | 20日 | 60日 | 5日胜率 | 信号次数 |
|:----:|:---:|:----:|:----:|:-------:|:--------:|
| 成长 | +8.61% | +7.66% | +10.99% | 82% | 11 |
| 周期 | +4.93% | +2.66% | +8.57% | 86% | 7 |
| 蓝筹 | +2.80% | +1.78% | +2.35% | 82% | 17 |
| 消费/其他 | +5.84% | +6.37% | +3.98% | 94% | 17 |

**观察要点**：
- 评分模型在不同市场环境下的表现是否一致？
- 如果某类股票评分失效 → 需差异化评分因子或动态权重
- 蓝筹股评分波动较小，成长股波动较大（双刃剑）
- **v1.1 发现**：蓝筹股60日收益仅+2.35%，远低于成长股+10.99%。缠论三买在低波动蓝筹中的效率天然低于高波动成长股——这在三维系统中应体现为基本面权重更高。

**关键技术决策：**

| 设计决策 | 选择 | 理由 |
|---------|:----|:-----|
| 采样频率 | **每个财报披露截止日**（4/30、8/31、10/31） | 财报每季度才出一份，评分的频率应与数据更新频率一致 |
| 时间区间 | 2021-04 ~ 当前（覆盖5年+） | 基本面的长周期属性需要长时间窗口验证 |

| 前视偏差规避 | **控制 Baostock 的 year/quarter 参数** | 不同于技术面的数据截断，基本面回测必须指定查询的财报年度/季度 |
| 评分来源 | 复用 `quick_fundamental.calculate_fundamental_score()` | 与实盘评分完全一致，无偏差 |
| PE/PB获取 | 从当日K线读取（不引入未来数据） | 估值因子属于"当时可观测"信息 |

**关键——前视偏差控制方法：**

### 实战经验总结

**基本面回测的典型发现：**
1. **半年窗口有初步区分度**——A组(推荐)在T+126上收益+13%，明显跑赢D组+6.49%，但样本少（仅7条）
2. **评分系统偏保守**——16个时点×18只股票=288次评分，从未出现80分以上（A+强推）
3. **基本面是慢变量**——个股评分对"公司好不好"的判断大体正确，但不适合短期择时
4. **与技术面互补**——技术面管短期（哪周买），基本面管长期（哪家公司好）

**股票池同步规则：** 两个回测脚本都从 `check_negative_news.py` 的 `MONITOR_LIST` 读取18只自选股（不是从 xlsx 读），与负面消息扫描共用同一份监控列表，三方永远同步。修改自选股只需改一处。

### 何时不做基本面回测

基本面回测与

**什么时候值得做：**
- 你有一个明确的「基本面选择 → 长期持有」策略，持有周期≥1年
- 你需要验证不同基本面因子的权重是否合理
- 你的策略是"选好公司"而非"择时"

**什么时候不做：**
- 你的系统已经包含技术面和消息面，基本面只作为安全垫（风控规则）——此时回测结论必然是"低分困境反转股反弹更大"导致分组混乱
- 观察窗口 < 6个月——基本面是慢变量，短期窗口验证不出有意义的结果
- 评分系统本身偏保守（如本系统的288次评分中从未出现80分以上）——没有高分样本来做统计对比

**实战经验：** 基本面回测最适合的落地方式是**不作为预测指标，而是作为风控规则**：
> 技术面决定"要不要买"，基本面决定"敢不敢重仓"
> - 基本面≥60 + 技术面≥70 → 重仓（30-50%）
> - 基本面<40 + 技术面≥70 → 轻仓（10-20%）
> - 技术面<60 → 无论基本面好坏，都不建仓

这条规则不需要回测验证，它是一个防御性的风控原则，不是预测模型。

**核心设计（区别于基于信号的轻量版）：**

| 设计决策 | 选择 | 理由 |
|---------|:----|:-----|
| 采样频率 | **每周一**，非每日 | 80个交易日 → 38周一，减少80%计算；缠论结构不会天天变，过滤噪音 |
| 分析入口 | 直接 `ChanLunAnalyzer.analyze(klines_list)` | 不依赖 `RecursiveTimingSystem`（后者会拉30min数据，增加耗时和复杂度） |
| 前视偏差规避 | 截取到 T 日的数据 `df.iloc[:pos+1]` | 每个采样点只用当时已知数据 |
| 收益计算 | `df.iloc[pos + N]` 定位 T+N 日收盘价 | 利用 iloc 整数位置，不受交易日缺失影响 |
| 30分钟共振 | **跳过**（回测中暂不处理） | 30min数据获取在批量回测中显著增加耗时，区分度已足够 |

## 跨模块一致性审计（v2.1 新增）

在运行任何回测验证之前，必须先确认：**回测使用的评分，是否与实盘系统使用的评分完全一致？**

### 核心原则

> 你验证的是回测脚本里的评分 → 但实盘用的是另一个评分 → 验证结论对实盘无效。

### 检查清单

逐模块对照以下检查表：

| 检查项 | 问题 | 常见不一致 |
|:-------|:-----|:----------|
| **评分函数** | 回测脚本和实盘系统调用的是同一个 `calculate_xxx_score()` 吗？ | 回测用 `calc_tech_score()`（简化版），Agent 用 `compute_technical_score()`（完整版） |
| **权重方案** | 回测的 W_tech/W_fund/W_news 和 SKILL.md/Agent 提示词中的一致吗？ | 一个文件改了另一个忘了同步 |
| 替代变量 | 回测是否用了替代变量而非真实数据？ | `confidence*20` 替代基本面评分，50 硬编码替代消息面评分 |
| **Baostock 登录状态** | 不同模块间 Baostock session 是否共享？退出/重登后连接是否仍有效？ | DataManager 在回测阶段已调用 `bs.login()`，后续 `grid_search` 中的 `get_financial_data()` 可能遇到 `you don't login.` 错误——需检查 error_code 而非仅 catch 异常 |
| **数据源** | 回测使用的数据获取函数和生产环境相同吗？ | 回测用缓存，生产用实时 API |
| **评分范围** | 各维度评分的 min/max 一致吗？ | 技术面 [-30,100]，基本面 [0,100]，综合时未归一化 |
| **前视偏差** | 回测是否用了 T 日之后的信息？ | K线截取正确但财报查询传了未来 quarter |
| **阈值/分级** | A/B/C/D 各组的阈值和实盘决策阈值一致吗？ | 回测用 <50=D，实盘用 <40=轻仓 |

### 发现方法：数据流追踪

逐模块画出「数据从哪来→经过什么函数→参与什么计算」的图：

```
实盘路径:   K线数据 → quick_chanlun.py → Agent评分 → W_tech*40% → 决策
回测路径:   K线数据 → score_backtest.py::calc_tech_score() → 分组统计
                                            ↑
                                    这两者一致吗？
```

### 典型发现：grid_search.py 替代变量偏差（实战案例）

**现象**：网格搜索找到「基本面40%权重最优」，但实盘中基本面权重提高反而信号更少。

**根因**：`grid_search.py` 用 `confidence * 20` 当基本面评分，而非调用 `quick_fundamental.calculate_fundamental_score()`。置信度来自30分钟级别确认（技术面概念），和财务数据完全不相关。

**修复**：将网格搜索中的 `conf_score = confidence * 20` 替换为实际调用 `quick_fundamental.calculate_fundamental_score(data)['total_score']`。

### 典型发现：两份技术评分函数并存（实战案例）

**现象**：`score_backtest.py::calc_tech_score()` 和 `validate_tech_score.py::compute_technical_score()` 是两套不同的评分逻辑。前者简单加减分，后者多维度加权。

**风险**：回测验证的是简化版，实盘 Agent 用的是完整版。如果两者对同一信号给出不同评分等级，回测结论不可信。

**修复**：二选一，统一入口。推荐保留 `compute_technical_score()`（更完整），让 `calc_tech_score()` 改为调用它。

## 常见陷阱

### 陷阱0：Baostock 字段位置索引不可靠（2026-04-29 发现）

**现象**：用 `row[2]` 取 EPS、`row[3]` 取 ROE——看似正确，但 Baostock 的字段顺序随接口版本/数据范围变化。实战中 `query_profit_data(2025Q3)` 返回的 `row[2]` 是 `statDate`（日期字符串）而非 `epsTTM`，导致 `safe_float("2025-09-30")` 返回 None，所有基本面评分变成默认值。

**根因**：Baostock 接口返回的列顺序因 year/quarter 参数而异。`query_profit_data` 的 `epsTTM` 在 row[7] 而非 row[2]。

**修复**：**总用字段名，不用位置索引**。
```python
# ❌ 错误：位置索引
eps = quick_fundamental.safe_float(row[2])  # row[2] 可能是 statDate!

# ✅ 正确：字段名查找
fields = [f.strip() for f in rs.fields]
vals = dict(zip(fields, row))
eps = quick_fundamental.safe_float(vals.get('epsTTM'))
```

**适用范围**：所有 Baostock 接口——`query_profit_data`, `query_growth_data`, `query_balance_data`, `query_cash_flow_data`。`fund_backtest.py` 中已有正确实现，`grid_search.py` 中的 `get_financial_data()` 曾受此问题影响。

### 陷阱1：评分集中在窄区间
如果所有信号评分落在 74-79 和 56-62 两个孤立区间，中间没有过渡，说明评分因子的区分粒度不够。应该增加量价、波动率等连续型因子来分散评分。

### 陷阱2：置信度区分度差
如果所有信号的置信度几乎相同（如全是 2/5），则多级别共振因子没有有效发挥。需要检查次级别确认逻辑是否太保守。

### 陷阱3：信号类型未细分
如果所有买点都显示为 `buy` 而没有一买/二买/三买的区分，说明分类器没有正确工作。检查买卖点类型分配逻辑。

### 陷阱4：样本量不足
少于 20 个信号的相关性分析统计意义有限。尽量覆盖 10+ 只股票、30+ 个信号。

### 陷阱5：正向偏差
如果评分系统只在特定股票（如高波动成长股）上有效，在蓝筹/周期上无效，说明评分因子可能无意中过拟合了某类股票特征。

### 陷阱6：置信度固化（v1.1）
如果 85%+ 的置信度集中在同一个分数（如 2/5），说明次级别确认逻辑过于保守。在 A 股日线+30min 框架下这个现象很常见——因为30分钟级别很少产生独立的买卖点。**解法**：新增 MACD 柱收缩确认作为第三层，将部分 "none" 提升到 "divergence" 级别。

### 陷阱9：股票类型硬编码分类（2026-04-29 发现）

**现象**：`validate_tech_score.py` 的"按股票类型汇总"使用硬编码集合：
```python
cyclical_codes = {"600309", "600346", "600486"}
growth_codes = {"300059", "601615", "300772"}
blue_codes = {"601318", "601601", "000001", "002415"}
```
新增自选股不在任何集合中 → 全部归入"其他" → 不参与类型对比 → 报告中的"蓝筹 vs 成长 vs 周期"统计只覆盖 10/18 只股票。

**根因**：两套分类系统独立运行——`quick_fundamental.classify_stock_type()` 数据驱动但不被 validate 调用；validate 用硬编码手工维护。

**统一方案**：
1. 创建 `classify_by_industry(industry_str)` 轻量函数——仅需行业字符串即可分类
2. `validate_tech_score.py` DEFAULT_STOCKS 改为含行业字段的三元组 `("600309", "万华化学", "化工")`
3. 对每只股票调用 `classify_by_industry(industry)` 得到类型
4. 将 `stock_type` 附加到每个信号结果，报告分组改为动态聚合
5. 行业映射补充："消费""金融"→蓝筹；"地产"→周期；"安防"→成长

如果 90%+ 的样本被判定为「回避」，评分分布严重左偏，说明扣分项叠加太重。

#### 典型现象（2025.08~2026.04，8只A股，38周×8只=304条）

| 分组 | 原始扣分 | 样本占比 | T+20收益 |
|:----|:--------:|:--------:|:--------:|
| A(推荐) ≥70 | 1.6% (5条) | +8.14% |
| B(关注) 60-70 | 3.0% (9条) | +6.87% |
| C(观望) 50-60 | 2.0% (6条) | +8.56% |
| D(回避) <50 | **90.8% (276条)** | +0.47% |

A组 vs D组 T+20 差 = **+7.67%** —— 评分在**相对排序**上有效，**绝对阈值**太严。

#### 首次修正：扣分项全部减半（已验证）

| 扣分项 | 原值 | 减半后 | 基于什么考虑 |
|:------|:----:|:------:|:------------|
| 向下笔破前低 | -5 | **-3** | 最轻微的信号，扣分象征性即可 |
| 跌破中枢下沿 | -15 | **-8** | 中枢破位是强信号但原值过度惩罚 |
| 卖点未突破 | -15 | **-8** | 同上 |
| 连续3笔向下 | -10 | **-5** | 趋势下行确认，但叠加上方3项后过重 |
| 无中枢结构 | -10 | **-5** | 不可分析状态应扣分但不致命 |
| 顶背驰未修复 | -15 | **-8** | 背驰信号重要但不宜一票否决 |

#### 修正后结果对比

| 指标 | 修正前 | 修正后 | 变化 |
|:----|:------:|:------:|:----:|
| D组占比 | 90.8% | **78.0%** | ↓12.8pp ✅ |
| A+B+C合计 | 6.6% | **8.9%** | ↑ |
| A-D区分度(T+20) | +7.67% | **+5.45%** | 略降但仍有效 |
| 个股最低均分 | 万科A **-15.9** | 万科A **+0.87** | ✅回归合理 |
| 紫金矿业均分 | 39.2 | **41.5** | 保持高分 |

#### 实战经验：筛选严格 vs 宽松

用户反馈：「筛选要求严格一些更好」——确认维持 D 组阈值 <50，不做进一步放松。这意味着：
- 评分系统的**相对排序**（A > B > C > D）用于横向对比
- **绝对分级**（D组定义）作为安全底线，宁严勿松
- 后续可以按季度重新跑回测，只监控区分度是否退化，不改阈值

#### 解决方案（按复杂度排序）

1. ⚡ **已验证推荐**：扣分减半（保留相对排序，改善绝对分布）
2. 下调决策阈值（如 D 组 <50 改为 <30）——不改变评分，只调整映射
3. 增加加分项（如"长期均线上方" +10）——需要重新验证

**验证方法：** 调整后重新运行 `score_backtest.py`，对比分组分布和 A vs D 区分度。
如果数据集中全部是同一类信号（如全是三买），这不是程序错误——在特定时间窗口内这是正常现象。但单一信号类型意味着评分模型的区分度本质上只能在中枢位置和量价上做文章。**解法**：扩大时间窗口（如回测 3-5 年数据）增加一买/二买出现的概率；或在三买内部增加中枢位置细粒度分级。
