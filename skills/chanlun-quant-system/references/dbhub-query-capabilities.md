# DBHub 查询能力边界 (2026-05-20)

## 背景

DBHub 是 SQLite 的 MCP 网关，裸 SQL 执行器，**不认识任何缠论概念**。
所有缠论概念（底分型、三买、中枢等）必须翻译成 SQL 或 Python 逻辑。
本文档分类记录：什么查询 SQL 能精确回答，什么需要近似，什么必须用 Python。

## 一、SQL 精确可查询（WHERE/ORDER BY/LAG/AVG 直译）

这类查询可以直接翻译成 SQL 条件，结果 100% 精确（数据本身准确的前提下）。

### 纯数值筛选

| 查询意图 | SQL 示例 |
|----------|----------|
| 股价在某个区间 | `WHERE close BETWEEN 10 AND 20` |
| 成交量排名 | `ORDER BY volume DESC LIMIT 10` |
| 涨跌幅条件 | 需自己计算条件值（如 `close/open - 1 > 0.05`） |
| 历史极值 | `ORDER BY close DESC LIMIT 1`（历史最高收盘价） |

### 相邻 K 线比较（LAG/LEAD 窗口函数）

| 查询意图 | 解释 |
|----------|------|
| 跳空缺口 | `curr_low > prev_high` — 今日最低价 > 昨日最高价，精确 |
| 放量 | `curr_volume > prev_volume * 2` — 成交量翻倍，精确 |
| 创新高 | `curr_high > MAX(prev_highs_20d)` — 20日新高，精确 |
| 连续涨跌 | 用 LAG 检查收盘价连涨/连跌天数 |
| 涨跌家数 | 今日收盘 > 昨日收盘计数 |

### 移动平均/窗口聚合

| 查询意图 | SQL 实现 | 精度 |
|----------|----------|------|
| 站上/跌破均线 | `close > AVG(close) OVER (20d)` | 精确 |
| 乖离率 | `close / AVG(close) - 1` | 精确 |
| 放量 vs 5日均量 | `volume > AVG(prev_5_volumes) * 1.5` | 精确 |
| N日振幅 | `MAX(high) - MIN(low) OVER (Nd)` | 精确 |
| 均线多头排列 | `MA5 > MA10 > MA20 > MA60` | 精确（需分别计算均线再比较） |

## 二、SQL 能做但需近似（简化版，非严格缠论）

这些查询 SQL 可以给出"八九不离十"的结果，但严格缠论定义需要 Python。

| 查询意图 | SQL 简化实现 | 缺失了什么 |
|----------|--------------|-----------|
| 简化顶/底分型 | `prev_high < curr_high AND next_high < curr_high`（顶）<br>`prev_low > curr_low AND next_low > curr_low`（底） | 包含处理（K线合并）—— 相邻K线若有包含关系，分型会误判 |
| 简化 MACD 金叉 | 数据表里没有 MACD 列，需先算出 | — |
| 简单连续形态 | 连续3根阳线/阴线 | 不涉及结构，纯统计近似 |

**典型用例**：本交易日做的 `日线底分型 (SQL简化版) + 放量 > 5日均量 × 1.5`，用 SQL 初筛出候选集，再交给 Python 做严格三买验证。这是高效的混合策略。

### 简化底分型的误差来源

```
K线:         K1       K2       K3
简化判断:     ↓        ↓        ↓
            prev_low > curr_low < next_low

实际误差:
  - 相邻K线有包含关系（如 K2 包含 K1）→ 需要先合并再判断分型
  - 合并后的分型判定可能完全改变（跨多根K线的复杂包含）
  - 严格缠论要求分型确认（分型后需要至少1根反向K线确认）
```

误差率估计：在数据量大（>500股）时简化底分型的**假阳性率约30-40%**（产生的结果中约1/3在严格定义下不成立）。但作为初筛过滤器，可以接受。

## 三、必须 Python 迭代（SQL 做不到）

这些需要**链式递归逻辑**：先判定 A，再用 A 判定 B，再用 B 判定 C。
SQL 的窗口函数无法表达这种迭代结构。

| 概念 | 为什么 SQL 不行 | 替代方案 |
|------|----------------|---------|
| **三买** | 需要：识别笔 → 中枢 → 突破 ZG → 回踩不进 ZG → 反弹，五步链式逻辑 | Python 滑动窗口法（见本次会话实现） |
| **一买/二买** | 趋势识别（≥2个中枢下移）+ 背驰判断（MACD面积比较）+ 回调不创新低 | Python `_find_first/second_class_points()` |
| **严格底分型** | 需要递归包含处理（合并后可能继续包含，直到无包含为止），SQL 无法表示 | Python `_merge_klines()` → `_find_fenxings()` |
| **笔** | 底分型→顶分型→底分型序列 + 成笔条件（≥5合并K线/幅度>5%） | Python `_find_bis()` |
| **线段** | 特征序列 + 包含处理 + 线段破坏判断，递归多次 | Python `segment_analyzer.py` |
| **中枢** | 3笔重叠 + 延伸逻辑（循环检查） | Python `_find_zhongshus()` |
| **背驰** | 两段走势的进入段 vs 离开段 MACD 面积比较 | Python `_calculate_macd_area_for_bi()` |
| **形态识别（头肩顶/W底等）** | 曲线拟合 + 几何规则匹配 | Python 逐段比对 |

### 分界线的本质

> **WHERE / ORDER BY / LAG / AVG 能直接表达的数值比较 → SQL 精确**
> **需要"先判定A再用A判定B"的链式逻辑 → Python 必须**

```
                        SQL 擅长              Python 擅长
                         │                         │
                         ▼                         ▼
              ┌─────────────────────┬──────────────────────┐
              │  数值直比较            │  链式递归              │
Examples:     │  放量/缩量             │  三买（笔→中枢→突破→回踩） │
              │  跳空缺口              │  严格底分型（包含处理）     │
              │  站上均线              │  背驰（面积比较）         │
              │  N日新高/新低           │  线段划分                │
              │  连续涨跌              │  形态识别                │
              └─────────────────────┴──────────────────────┘
```

## 四、混合策略推荐（最高效方案）

```
┌─────────────────────────────────────────────────────┐
│                 Step 1: SQL 初筛                      │
│  简单数值条件（放量/站上均线/底分型简化版）               │
│  输出：候选股列表（可能是假阳性，没关系）                  │
└────────────────────┬────────────────────────────────┘
                     ↓ 候选集（大幅缩小范围，如 515 → 10 只）
┌────────────────────┴────────────────────────────────┐
│                 Step 2: Python 精筛                  │
│  严格缠论分析（包含处理/笔/中枢/买点）                   │
│  输出：真实符合条件的股票列表                             │
└─────────────────────────────────────────────────────┘
```

**本次会话实测**：SQL 初筛从 515 只日线+48 只重叠 30min 数据中，先筛出 4 只候选，Python 精筛后确认 5 只类三买。如果纯用 Python 遍历 515 只，每只都需要完整的 `get_klines()` + 缠论分析，耗时从几秒变成几十分钟。
